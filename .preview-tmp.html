CASE 01 Alpha de integração

Postais da Parnaíba

Contexto e problema

Experiência editorial para preservar e apresentar a memória histórica de Parnaíba: conteúdo, imagens e narrativas em uma leitura navegável.

O que construí

  • Site multipágina com conteúdo editorial e acervo visual
  • Slider, comparador antes/depois, galeria, timeline e crônicas via contrato HTTP
  • Painel cliente para CRUD de conteúdo e upload de imagens

Ponto técnico

HTML estático para o editorial e JavaScript separado para as coleções dinâmicas, sem etapa de build. A API fica fora do repositório e usa localhost por padrão.

Stack

  • HTML
  • CSS
  • JavaScript
  • Fetch API

CASE 02 Protótipo backend

BeckGlobal

Contexto e problema

Um boilerplate para estruturar APIs REST com persistência, configuração e ambiente containerizado. Escopo autoral: setup da API, CRUD, modelo, sessão e configuração, com SQLite atual e PostgreSQL declarado no Compose.

O que construí

  • FastAPI, schemas Pydantic e CRUD de usuários
  • Modelo e sessão SQLAlchemy com respostas sem senha
  • Hash bcrypt e primitivas para emissão e leitura de JWT
  • Dockerfile e Compose declarando API e PostgreSQL

Ponto técnico

Separação entre API, core, database e models; as rotas acessam o ORM diretamente, sem services ou repositories. Limite atual: a migração inicial está vazia, o JWT não protege rotas e ainda não existem testes automatizados ou CI.

Superfície HTTP

6 endpoints da aplicação
GET/healthhealth check
POST/users/criar usuário
GET/users/listar usuários
GET/users/{user_id}consultar usuário
PUT/users/{user_id}atualizar usuário
DELETE/users/{user_id}excluir usuário

Stack

  • Python
  • FastAPI
  • Pydantic
  • SQLAlchemy
  • Alembic
  • Docker

Decisões técnicas
Escolhas observadas no código
  • Separação inicial entre API, core, database e models.
  • Responses públicas excluem o hash de senha.
  • Sessão síncrona injetada como dependência por requisição.
  • Lockfile Poetry e ferramentas locais de lint e pre-commit.
Desafios atuais
O que impede um fluxo completo
  • A migração inicial não cria a tabela users.
  • Não existe rota de login e nenhuma rota exige JWT.
  • SQLite está selecionado enquanto o Compose provisiona PostgreSQL.
  • Não existem testes automatizados nem pipeline de CI.
Evidências
Onde verificar
  • app/api/routes/users.pyCRUD direto no ORM
  • app/core/security.pybcrypt e JWT
  • app/database/engine e sessão
  • docker-compose.ymlAPI e PostgreSQL

Estado atual: scaffolding legível, mas sem schema executável ou autenticação aplicada.

CASE 03 Unicesumar × Qlik

Hackathon FUNDEC/RS

  1. Fontes públicas
  2. ETL em Python/pandas
  3. Dataset analítico em SQLite
  4. Qlik Cloud
  5. Dashboard

Contexto e problema

2º Hackathon Unicesumar em parceria com a Qlik, tema transparência e equidade na reconstrução do Rio Grande do Sul. Projeto em equipe de 3 sobre os repasses do FUNDEC (Fundo Estadual de Defesa Civil do RS) após as enchentes de 2024: 658 movimentações em 334 municípios, entre maio e setembro de 2024.

O que construí na equipe

  • Pipeline de ETL em Python/pandas sobre as fontes públicas do FUNDEC
  • Modelo analítico em star schema no SQLite (fato + dimensões) e CSVs de carga
  • Validações automatizadas e conciliação entre fato e ranking oficial
  • Carga dos CSVs no Qlik Cloud e documentação técnica do projeto

Ponto técnico

Star schema com fato de repasses e dimensões de município e calendário; os 18 estornos são preservados com sinal negativo e o fato é conciliado com o ranking oficial. No Qlik Cloud, a carga usa a conexão DataFiles com CSV UTF-8 e as tabelas se associam por chave_municipal.

Stack

  • Python
  • pandas
  • SQLite
  • Qlik Cloud
Equipe Excelsior (3 integrantes): ETL e modelo analítico · análises e telas no Qlik · dados e pitch
